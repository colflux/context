01 · Martín Otálora

El modelo de datos: la base de todo lo demás

Antes de mostrar un mapa o una gráfica, hubo que definir qué es un dato válido para COLFLUX: qué categorías, qué regiones, qué nivel de confiabilidad.

Resuelto

Categorías y regiones

Modelo de datos por categoría (biomasa, COS, MOM, flujos GEI) cruzado con las 3 regiones de trabajo del proyecto (Andes, Orinoquía, Amazonas), sembrado en migraciones del backend.

Resuelto

Roles y niveles de acceso

Migración de roles múltiples a un esquema de nivel en cascada (ciudadano < investigador < reportador < admin), aplicado consistentemente en permisos de API.

3-6 meses

Calidad y trazabilidad

Falta el criterio real de confiabilidad (hoy es estado binario) y el registro de quién subió cada dato y cómo se capturó.

Pendiente de decisión

Tensión login vs. datos abiertos

El grupo de Nariño pidió restringir todo acceso sin login — choca con el principio de datos abiertos del proyecto. Sin resolver esto no se puede diseñar el nivel de acceso graduado (F19).

02 · Andrea Chaparro

Subida de datos: de Excel a la base productiva

El flujo de ETL conecta el trabajo de campo (archivos Excel por categoría) con el backend, sin gaps de endpoints.

En producción

Carga y descarga por categoría

Interfaz /etl/datos mapeada 1:1 con los endpoints del backend Django ya existentes — sin necesidad de construir infraestructura nueva.

En producción

Formatos validados

Exportación/importación respeta el formato esperado por categoría, reduciendo errores de carga manual.

0-3 meses

Formulario "Reportar" conectado

Hoy el formulario de reporte de campo solo guarda estado en memoria — falta conectarlo al endpoint real para que los datos capturados en campo entren directo al flujo de ETL.

3-6 meses

Georreferenciación automática

Captura de coordenadas GPS en formularios de campo, para que el dato llegue ya ubicado en el mapa sin paso manual.

03 · Alejandra Díaz

Despliegue: de "funciona en mi máquina" a producción estable

Backend, frontend e ia-functions corren hoy en un solo servidor (Lightsail), detrás de nginx, con deploy automático en cada merge.

Resuelto

CI/CD por repositorio

Workflows de GitHub Actions para backend, frontend e ia-functions, cada uno con su propio deploy automático verificado end-to-end.

Resuelto

Base de datos productiva (RDS)

Conexión blindada a PostGIS en AWS RDS, con smoke test en cada deploy y fallback fuerte si falta configuración — ya no falla en silencio.

Resuelto

Seguridad de red por diseño

Servicios internos atados a 127.0.0.1 y enrutados por nginx — ningún puerto nuevo expuesto públicamente, lección aplicada tras un bug temprano de frontend.

Crítico — 0-3 meses

Autenticación real de la API

La API todavía puede mutar datos sin autenticación real en varios endpoints — es el hueco de seguridad más urgente antes de abrir la plataforma más ampliamente.

05 · Viviana Bautista

Estado general del prototipo

Todo lo mostrado corre hoy en producción real — no es un mockup.

Ya existe y funciona

  • Mapa interactivo de ecosistemas (geoportal base)
  • ETL de carga/descarga de datos por categoría
  • Módulo de gráficas y reportes
  • Roles de usuario y credenciales admin
  • Conexión a base de datos productiva (RDS)
  • Automatización de deploy (backend, frontend, ia-functions)

Trabajo a medias (prioridad inmediata)

  • Seguridad real de la API (crítico)
  • Recuperación de contraseña self-service
  • Formulario "Reportar" conectado al backend
  • Decisión sobre reactivar Insights (IA)
  • Manual de usuario del flujo de reporte
05 · Viviana Bautista

Roadmap: 3 / 6 / 12 meses

Criterio: cerrar primero el MVP ya iniciado antes de abrir módulos nuevos (sensores IoT, colaboración interinstitucional, chatbot).

0-3 meses · Cerrar lo iniciado

  • Seguridad de la API (crítico)
  • Recuperación de contraseña
  • Formulario "Reportar" → backend real
  • Manual de usuario
  • Decisión: Insights sí/no

3-6 meses · Módulos base

  • Calidad y trazabilidad de datos
  • Wiki de conocimiento + glosario
  • Captura GPS en formularios de campo
  • Restricción de edición + comentarios
  • Exportación de metadatos metodológicos

6-12 meses · Módulos nuevos

  • Alertas y notificaciones (WhatsApp)
  • Monitoreo de red / sensores IoT
  • Colaboración interinstitucional
  • IA conversacional ampliada
  • RBAC completo (~18 actores)
Para el director

Decisiones que necesitamos de tu parte

Puntos que condicionan el roadmap y no se pueden resolver solo desde el equipo técnico.

  • Login vs. datos abiertos — el grupo de Nariño pidió restringir todo acceso sin login; choca con el principio de datos abiertos del proyecto. Sin definir esto, los niveles de acceso graduados (F19) y el RBAC completo (F58) no se pueden diseñar con certeza.
  • Causa de la desactivación de Insights — apagado el 20/09/2026. Si es un problema de costo o estabilidad del proveedor de IA, condiciona si el módulo de IA ampliada (chatbot, F54-F56) se construye con el mismo proveedor o se cambia.
  • Vigencia de CU-07/CU-08 — incidencia territorial y colaboración interinstitucional están marcados en el catálogo de funcionalidades como "se plasma si se requiere", sin confirmar como scope real. Necesitamos tu validación antes de invertir en el bloque de 6-12 meses.
  • Sostenibilidad post-financiación — ninguna funcionalidad del roadmap resuelve el plan de mantenimiento técnico una vez termine la financiación actual. Es una conversación aparte que hay que agendar.
